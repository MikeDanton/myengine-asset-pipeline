# Producing the first real game assets

Last reviewed: 2026-11-19.

Our image-production pipeline is already capable of packaging real PNGs. There are
two ways to obtain them today. Neither requires modifying MyEngine2, platformer,
or SimGame runtime code.

## Option A: use ChatGPT image generation manually (recommended first)

Ask ChatGPT to generate **one asset at a time** with an unambiguous visual
specification. Download/save the produced PNG to a local, reviewable game's
`source/` directory. This path uses the existing `ai-import` source adapter
and does not require OpenAI API billing or any CLI credentials.

Suggested starting prompt for the platformer (edit to match its actual style):

> Original hand-painted 2D fantasy platformer prop: an ancient wall-mounted
> iron torch, simple readable silhouette, warm amber flame, front-facing game
> sprite, no text, no frame, isolated on a truly transparent background, single
> prop fully inside the canvas with generous transparent margins. Consistent
> materials and lighting, suitable for a small side-scrolling game.

Generate a rune and door with the **same style guide** rather than independently
improvising each prompt. Inspect transparency and edge artifacts at actual game
scale. Keep high-resolution masters; avoid asking the image model to generate a
finished 16-frame sprite sheet until we have evaluated visual consistency.

Record the exact prompt text in a **local** prompt file, compute its SHA-256,
and write a versioned `ai-import` entry in the game's `assets.json`.
Record the actual generation product/model if known (or `ChatGPT Images,
model not exposed` rather than guessing) and verify distribution rights.

```sh
sha256sum game-art/prompts/torch.txt
python3 tools/assetprep.py game-art/assets.json build/approved \
  --provenance build/asset-provenance.json --replace
python3 tools/atlasprep.py build/approved game-art/environment-atlas.json \
  build/pack-ready --replace
build/tools/assetc/assetc build/pack-ready build/platformer.pak
```

The above tool paths are relative to this asset-pipeline checkout. Adjust if
running from a sibling game repository. `atlasprep` requires Pillow at build
time; `assetprep` and `assetc` use the existing dependencies documented in
the README. No generation service is invoked by these three commands.

## Option B: generate one real PNG from a paid image API

The optional `openai-images` adapter calls the **current OpenAI Image API**
`POST /v1/images/generations`, currently with a low-quality transparent
1024x1024 PNG and model `gpt-image-2.6-flare` or
`gpt-image-2.6-sunburst`. It deliberately makes **only one request**, with
**no automatic retries**, and never promotes the image to approved assets.

Save a **local, non-secret-free generation spec** at
`game-art/requests/torch-openai.json` (the text prompt may be private):

```json
{
  "version": 1,
  "job_id": "platformer-torch",
  "provider": "openai-images",
  "model": "gpt-image-2.6-flare",
  "prompt": "Original 2D fantasy platformer wall torch sprite, transparent background, no text, front-facing, simple silhouette, generous margins",
  "width": 1024,
  "height": 1024,
  "candidate_count": 1,
  "seed": 0,
  "budget": {"max_candidates": 1, "max_cost_usd": 0.5}
}
```

Run only when ready to pay for the image:

```sh
# Read the key from a secret manager or prompt without echoing it in shell history.
read -rs OPENAI_API_KEY; echo; export OPENAI_API_KEY
python3 tools/assetgenerate.py game-art/requests/torch-openai.json \
  build/unreviewed/torch --allow-paid-generation
unset OPENAI_API_KEY

python3 tools/candidate_review.py build/unreviewed/torch build/review/torch
```

The API key is read from the environment and must never be committed. This
integration does **not** use the ChatGPT subscription: image API usage is
billed separately. It may require image API account access and organization
verification. Images are never generated by CI or by merely opening this spec.

**Cost caveat:** The `max_cost_usd` field is a *preflight allowance*, **not
a guaranteed billing ceiling**. The adapter currently requires at least
$0.50 of authorization per one-image request. It does not mean a $0.50
charge. We calculate a post-response token-based estimate when usage is
available, and otherwise label the $0.50 allowance as an estimate.
Actual billed amounts can differ. No retries occur, and a single request
can still cost more than its estimate. Check the current provider pricing
before opting in. The API may not support replayable seeds: the receipt
records `seed: null`, not an invented deterministic seed.

## Common review/packaging boundary

Both options still require a human to inspect the image at full resolution,
approve it for the game's art direction, review source/provider distribution
rights, copy it to the reviewed source collection, and complete the
`ai-import` source manifest. The generated candidate directory and
contact-sheet directory each contain a quarantine marker; `assetc`
refuses to package either.

A real generated image may contain background residue, inconsistent outlines,
painted shadows, or animation inconsistencies. Resize/crop/slice only during
a deterministic **build-time** transformation, and review the in-game
appearance before accepting a public release.

### Turning a generated 1024px master into a game sprite

The new atlas stage can resize each approved PNG frame without changing its
high-resolution source. Add this sprite to the game's atlas layout, alongside
other approved sprites:

```json
{"id": "torch", "source_key": "sprites/torch.png",
 "frame_width": 1024, "frame_height": 1024, "frame_count": 1,
 "output_width": 128, "output_height": 128,
 "resize_filter": "lanczos", "pivot": [512, 960]}
```

The generated atlas records a 128x128 frame and converts the pivot to [64,120].
Use `nearest` for true pixel-art sources. Image resampling is deterministic
under the pinned Pillow version, but still requires visual inspection in-game.
The original 1024px image remains unchanged in the approved source collection.

## SimGame follow-up

Use the same exact process for a small, bounded visual family, e.g. one
wetlands plant sprite and two stone/wood materials. SimGame decides which
variant to use from biome/culture data; it should never call a model during
world simulation. Once one family renders correctly, add consistent asset
variants rather than producing unique uncontrolled artwork for every object.
